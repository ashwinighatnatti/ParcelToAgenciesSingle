Single-Collector Pipeline: Feature Specification

What is implemented, how each feature was verified, and what it cannot do yet. Covers the search pipeline (single_collector) and its Django web UI (django_ui). Written 2026-11-17 for the three-stage design. This is a capability check, not a production system.

1. Overview and status

The system finds the tax collecting agency for a property, starting from a parcel address, a parcel ID, or both. It runs three stages: validate_address, find_validate_parcel, find_validate_agency. It does not use a fixed list of states or agencies: the county comes from the US Census, the parcel from the county's own records, and the agency from the county's statement page (or, for a county without an adapter, from Claude's live web research).

Bottom line from testing. For the two adapter counties (Maricopa AZ, King WA) every route works end to end and results are verified: parcel found in the county's records, agency read from the county's statement, parcel number confirmed on it, bill PDF saved. For any other county the pipeline still finds a parcel and agency by web research, but labels them found_unverified and usually cannot retrieve a bill. When an address has no parcel (the reported 4800 Ravenna Ave NE case), the result now explains why and suggests the nearest parcels instead of returning a blank.

2. How a search flows

  1. Stage 1, validate the address. The Census geocoder returns the normalized address and county; TIGERweb returns the city and school districts. Skipped when searching by parcel ID alone.
  2. Stage 2, find / validate the parcel. By parcel ID, by address, or both (cross-checked). Returns the parcel ID and the parcel's own address. No parcel, or several, gives a reason and the nearest parcels.
  3. Stage 3, find / validate the agency. The agency is read from the county's statement page and checked against the parcel number. The statement is saved as a PDF.

The data-flow diagram and six worked examples are in Search_Flow.html.

4a. Confidence score and cost per search

Both are added to every result record as confidence and cost, and shown on the result page.

Confidence (0-100)

Points are earned for how strong the evidence is at each stage. A search by parcel ID has no address to check, so the address part is left out and the score is points earned divided by points possible. If no agency is found the score is 0, because there is no answer to be confident about.

EvidenceSituationPoints
Address (20)The Census geocoder matched the address20
Parcel (40)Found in the county's own records (GIS adapter)40
Parcel number read from the county portal through web research30
Parcel number from a third-party website15
Agency (40)Read from the county statement that shows this parcel40
Read from the statement, but the parcel number was not on the page10
Named by web research for this parcel20
Named by web research for the county only8
AdjustmentsThe parcel's address differs from the address entered-20
A separate city, school or special-district collector was reported-10

Levels: high 80-100, medium 50-79, low 0-49. The weights are a judgement, not a statistical calibration; they should be tuned once Operations' answers are compared with the scores.

Cost

Every Claude call goes through agent.ask, which records the usage the API reports. cost.py prices it per stage:

cost = (input tokens + 1.25 x cache-write tokens + 0.10 x cache-read tokens) x input price + output tokens x output price + web searches x search price

  • Prices default to $5 per million input tokens, $25 per million output tokens and $0.01 per web search (an Opus-class list price, assumed). Override with COST_INPUT_PER_MTOK, COST_OUTPUT_PER_MTOK, COST_WEB_SEARCH_EACH in .env and check them against the Azure invoice.
  • Input tokens are the hidden cost. A web search is not one call to the model: inside one request the model searches, reads the results, and searches again. Each search result is added to the context and billed as input, and the growing context is billed again at every step. One failed web research measured 26 searches, 1,395,129 input tokens and $7.53, almost all of it input tokens; the search fee was only $0.26.
  • Output tokens include narration. The model's text between searches is billed even though ask discards it.
  • Tool definitions are added to the prompt automatically and billed as input on every call.
  • Free: Census, TIGERweb and the county map services. The Playwright browser runs on your machine and is not billed.
  • Not measured: a call that raises an error returns no usage and is not counted; any charge Azure adds for code execution used by the dynamic-filtering search tool is not visible in the usage data.

Measured so far: a county-adapter search where Claude only reads the statement page, $0.012 (1 call, 1,410 input and 190 output tokens); an address in a county without an adapter, where Claude researches on the web, $7.53 in the run above (typically far less when the search succeeds quickly). Cost depends on how long the web search runs, not on the address. Each web research call is now capped at 6 searches and 4 page fetches (MAX_SEARCHES, MAX_FETCHES in portal.py); the same Orlando address then took 52 seconds, 4 searches, 100,142 input tokens and $0.60.

4b. Trajectory and audit file

Every result carries an audit block built by trace.py: steps, websites, web_searches and by_stage (a one-line summary per stage). Each step records its stage, the source, the action, what was asked, what came back and the URL. A Claude step also records the web searches it ran, the results it received, the pages it opened, the text it wrote, its tokens and its cost.

  • Where it shows: the Search tab explains the method (stages, confidence table, ranking rule); every result page has a Trajectory section; every job page has Download audit file (Excel).
  • Audit file sheets: Summary (one row per search), Trajectory (every step), Websites, Web searches, Confidence (points behind each score), Method.
  • The ranking explained: suggested parcels are ordered by how close their house number is to the address entered (same street, same ZIP), and the 5 nearest are shown; none is picked automatically. The Rank states tab is a separate ranking of states.
  • Limits of the record: web search and fetch run on Anthropic's side, so the record is what the API reports back. It lists the results a Claude call received, not which result came from which query. The newer search tools also run server-side code to filter results; this is counted (server_code_runs) but its billing is not visible.

6. Web UI

A Django app in django_ui/. A search can take minutes, so it runs as a background job: the page shows "Searching…" with elapsed time and reloads by itself when the job finishes. Each job runs the command-line pipeline in a separate process and stores the result in a local SQLite database.

PageWhat it does
SearchThe three search modes (the form shows only the fields each needs). Starts a job and shows the three stage results, the suggested parcels, and a link to the bill PDF.
Result pagePer-stage sections (validate address; parcel ID and address; agency), the bill link, flags and the full JSON. Suggested parcels have a "Search with this parcel" button that starts a new search by that parcel ID.
Quick checkStages 1 and 2 only, answered immediately, for counties with an adapter. A county without one is sent to the full search, because web research takes minutes.
BatchUp to 200 searches from typed addresses or an uploaded CSV, run as one job; shows a summary table with expandable details.
HistoryThe last 50 searches with their status; each opens its stored result.
Rank states, JurisdictionsThe state ranking (fetches live Census data when asked) and the 51-jurisdiction reference file.
  • Bills are served only from the downloads/ folder and only as PDFs; other paths return a 404.
  • A job left running by a server restart is marked failed rather than waiting forever.
  • The UI has no login and runs with DEBUG on. It is built for one user on localhost.

7. State ranking

python -m single_collector.rank_states (or the Rank states page) lists the states where one office collects the property tax, easiest first, using visible signals only:

  1. Gate: the state is marked single-collector in jurisdictions_config.json (25 of 51 jurisdictions; a draft that Operations should validate).
  2. Confidence in that classification (Tier 1A high, Tier 1B medium).
  3. Portals to cover: how many of the state's largest counties hold 80% of its housing units (live from Census TIGERweb).

First ten: DC (1 portal), Nevada (2), Arizona (4), Utah (6), Washington (10), Colorado (11), Wyoming (12), New Mexico (12), Oregon (12), Idaho (15). The search itself no longer reads this file.

9. Limitations and risks

  • Coverage: verified results exist for two counties. Elsewhere, results are web research: slower (minutes), labelled unverified, and vary between runs.
  • Each adapter is one county's page layout. A redesign breaks it. A failed adapter is flagged and web research takes over, which usually cannot retrieve a bill.
  • The agency is read by Claude from the page text. It is checked against the parcel number on the page, but the wording is the portal's own (for example "Treasury Operations" rather than "King County Treasury Operations").
  • Street matching is heuristic. It tolerates abbreviations but treats a differently named street as a different street; ranges, corner lots and unusual forms may need manual parcel entry.
  • "Single collector" is not "one agency" in Operations' data. A San Francisco parcel lists four agencies (secured, supplemental, unsecured, business tax), all billed by one office.
  • The earlier spec example was wrong: 4600 Silver Hill Rd is in Prince George's County, Maryland, not DC. The pipeline uses the Census state.
  • Privacy and terms: property addresses and parcel numbers go to the Census, county GIS services and portals, and the Claude deployment with its search tool. Confirm this fits your data policy and each portal's terms. The adapters make one lookup at a time with no rate-limit handling.
  • Cost and time are unmeasured. An adapter county takes about a minute per search; web research takes minutes. Token cost has not been measured.
  • The web UI has no access control. Run it locally only. For shared use it needs authentication, a real secret key, DEBUG off and a proper job queue.

10. Setup and how to run

Requirements

  • Python 3.14 with: anthropic, python-dotenv, requests, pandas, openpyxl, playwright, django. Run playwright install chromium once.
  • A .env in the project folder with the Azure AI Foundry settings (names only): AZURE_ANTHROPIC_API_KEY, AZURE_ANTHROPIC_API_ENDPOINT, AZURE_ANTHROPIC_DEPLOYMENT_NAME.
  • The Operations Excel file in the project folder (used only by the state ranking).

Commands (from the project folder)

python django_ui/manage.py migrate             # once: creates the job database
python django_ui/manage.py runserver           # the web UI at http://127.0.0.1:8000/

python -m single_collector.run "400 Broad St, Seattle, WA 98109"                        # by address
python -m single_collector.run --parcel 1985200495 --state WA --county King             # by parcel id
python -m single_collector.run "400 Broad St, Seattle, WA 98109" --parcel 1985200495    # both, cross-checked
python -m single_collector.run --file searches.csv                                      # address,parcel_id,state,county
python -m single_collector.portals 53033 --parcel 1985200495                            # one adapter alone
python -m single_collector.rank_states                                                  # state ranking

11. Open decisions and next steps

  1. Choose the next counties for adapters. Nevada (Clark, Washoe), Utah and Colorado rank high; check each portal for a bot challenge first. Each new adapter turns a county from found_unverified into success.
  2. Decide how to treat blocked portals (the county-taxes family): a data feed, an agreement with the vendor, or leave them on the web-research route.
  3. Settle what "bill" means. The adapters print the portal's tax statement page, which is not the mailed bill. Confirm that satisfies the requirement.
  4. Add automated tests for the stages, the parcel matching and the Django views, then measure cost and time per search.
  5. Decide whether an unmatched address should wait for a county-level agency. When no single parcel matches in an adapter county, the pipeline still researches the county's agency on the web, which took about 4.5 minutes in the Ravenna test, before showing the suggestions. The agency is only a county-level, unvalidated answer. Skipping it (the agency is read from the statement once a parcel is chosen) would return the suggestions in seconds.
  6. Retire the Streamlit UI once the Django UI is accepted, and clear the dead code listed in the developer guide.
  7. Before sharing the web UI: authentication, a real secret key, DEBUG off, and a job queue instead of worker threads.
