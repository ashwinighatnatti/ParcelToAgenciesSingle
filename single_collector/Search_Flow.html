Search Flow: steps and data flow

How the single-collector pipeline finds a parcel and its tax collecting agency, starting from a parcel address, a parcel ID, or both. Every example uses real output from test runs on 2026-11-17.

1. What changed and why

A search for 4800 Ravenna Ave NE, Seattle, WA 98105 returned the county but no parcel ID and no parcel address. The cause: the Census geocoder accepts an address by estimating a position along the street, but King County's own records contain no parcel numbered 4800 Ravenna Ave NE (the nearest are 4745, 4740, 4735, 4727 and 4711). The old code returned a blank with no explanation, and it never showed the parcel's own address even when a parcel was found. The agency shown came from fixed text in the code, so it appeared whether or not a parcel existed.

The redesign. The search is now three named stages, each of which validates what it finds and says why when it cannot:

  1. validate_address: is the address real, and where is it?
  2. find_validate_parcel: which parcel is it? Search by address, by parcel ID, or both (cross-checked). Returns the parcel ID and the parcel's address. When there is no exact parcel, it explains why and suggests the nearest ones.
  3. find_validate_agency: who collects the tax? Read from the county's own statement page and checked against the parcel ID.

No agency name or address is typed into the code, and there is no fixed list of states or agencies. The county, the parcel and the agency are all found at run time.

3. The three stages in detail

Stage 1: validate_address(query)

  1. If there is no address (a parcel-only search), the stage is skipped; the parcel's own address is validated after stage 2 finds it.
  2. The Census geocoder returns the normalized address, coordinates and county code. No match → valid: false and the search ends with invalid_address (unless a parcel ID was also given).
  3. TIGERweb takes the coordinates and returns the county, the incorporated city (empty means unincorporated) and the school districts.
  4. The state is read from the normalized address. If the user typed a different state or county, a flag is added and the Census answer is used.

Output: address_validation. A valid address here only means the Census can place it. The Census interpolates along the street, so the address might not exist as a parcel; stage 2 settles that.

Stage 2: find_validate_parcel(query, address_check)

  1. Find the county. From the validated address, or, for a parcel-only search, from the state and county the user gave: the Census resolves the name to a county code (King in WA → 53033). A parcel number is only unique inside one county, so without either, the status is county_needed.
  2. Choose the source. If the county has an adapter, search its parcel records (verified). Otherwise Claude searches the web (unverified).
  3. Search by parcel ID: the parcel either exists, with its address, or does not (not_found, with the reason). If an address was also given, the parcel's address is compared with it; a mismatch adds a flag.
  4. Search by address: take the distinctive word of the street (RAVENNA), fetch the parcels on that street in that ZIP, and keep those whose street name is at least 85% similar to the address. Then:
    • exactly one with the same house number → matched
    • several with the same house number (for example a condominium) → ambiguous, with all of them listed
    • none → not_found, with the five nearest house numbers on that street, and a reason

The code never picks a nearby parcel for the user: a bill for the wrong property is worse than no bill. The user chooses from the suggestions, or enters a parcel ID.

Output: parcel with status, parcel_id, parcel_address, full_address, verified, source, candidates, reason and, when both inputs were given, address_matches_input.

Stage 3: find_validate_agency(query, address_check, parcel)

  1. Parcel matched and the county has an adapter: open the county's statement page for that parcel in a headless browser. Claude reads the page text and returns the agency name, the office or payment address printed on it, the taxing bodies it itemises, and any other office it says collects part of the tax. The portal's address is taken from the page's own URL.
  2. Validate: the parcel number must appear on the statement page. Only then is the agency marked validated.
  3. Collector model: multiple if a separate collector is named; single if the statement itemises two or more taxing bodies on one bill; otherwise unknown.
  4. Save the statement as a PDF. If the portal script fails, the stage falls back to web research and says so in a flag.
  5. Parcel matched, no adapter: use Claude's web research from stage 2. Not validated; the bill link, if any, is downloaded.
  6. No single parcel: report the agency for the county only (county_level_search), clearly marked unvalidated, with no bill.

Output: agency (name, address, portal, taxing bodies, separate collectors, collector model, checks) and tax_bill.

6. What is dynamic and what is still fixed

Found at run timeStill fixed in the code
  • State, county, coordinates, city, school districts (Census)
  • County code from a state and county name (Census)
  • Parcel IDs, parcel addresses and nearby parcels (county records)
  • Agency name, office address and portal address (the county's statement page)
  • Taxing bodies and separate collectors (the statement page or web research)
  • The bill PDF (the statement page)
  • The county adapters. Two exist (Maricopa AZ, King WA): the address of each county's public GIS service and the clicks needed to reach the statement. Any other county goes through Claude's web research, which is slower and unverified. Adding a county is one new module.
  • Matching thresholds: street names 85% similar, five suggestions.
  • The Census boundary layer numbers.
  • The state-ranking tab uses a reference file of single-collector states. The search does not use it.

Removed in this redesign: the Tier 1 gate that skipped fragmented states, the agency name, address and portal text that was typed into each county script, and the single catch-all success status.

8. Limits

  • Only two counties are verified end to end. Elsewhere the parcel and agency come from web research and are marked unverified. A few of those lookups will be wrong; the status and flags are there so they are not mistaken for confirmed results.
  • A search can take minutes in a county without an adapter, and about a minute with one. Cost per search has not been measured.
  • The agency is read by Claude from the page text. It is checked against the parcel number on the page, but the wording (for example "Treasury Operations" rather than "King County Treasury Operations") is the portal's own.
  • Some portals block automation (San Francisco and Orange County FL sit behind a Cloudflare challenge). These would end in the web-research route and a missing bill; the project does not bypass such protection.
  • Street matching is fuzzy. It tolerates abbreviations (AVE/AV) but treats a differently named street (NE RAVENNA BLVD) as a different street. Unusual address forms (ranges, corner lots) may need manual parcel entry.
  • Property addresses are sent to the Census, the county services and the Claude deployment. Confirm this fits your data policy.
